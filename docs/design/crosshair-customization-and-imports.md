# Crosshair customization and easy imports

Research checkpoint, October 3, 2026 (America/Chicago). The owner requests a custom crosshair people can import easily, with Aimlabs, KovaaK's and VALORANT as references. [GDJ-18](https://linear.app/cnid/issue/GDJ-18/customize-and-share-crosshair-presets) holds the later implementation recommended here; this document adds no crosshair editor or import support to the current build. The accompanying [GDJ-16 revision](../playtests/2026-10-03-damaged-only-health.md) implements damaged-only normal-enemy HP.

## Findings from the reference products

| Product | Verified approach | Implication for our game |
| --- | --- | --- |
| VALORANT | Saved profiles with clipboard code export/import, an imported preview and profile naming. Riot later added custom RGB hex colors and separate horizontal/vertical line lengths. | Use a similarly short paste, preview and apply flow. Keep parameter presets editable. |
| Aimlabs | Official historical material documents pixel-based customization and imported crosshair images, including size adjustment and recoloring. | Define size units clearly and support transparent images for static appearance. |
| KovaaK's | Its current official web creator has layered shapes, pixel dimensions, color/opacity, outlines, offsets and custom PNGs, with previews, PNG download and sharing. Its FAQ documents PNG installation and share links. | PNG is a useful bridge; a layered artist's editor is more scope than the first in-game settings panel needs. |

VALORANT evidence: [3.03, August 10, 2021](https://playvalorant.com/en-us/news/game-updates/valorant-patch-notes-3-03/) documents multiple profiles and advanced ADS/scope options; [4.05, March 22, 2022](https://playvalorant.com/en-us/news/game-updates/valorant-patch-notes-4-05/) documents copying generated codes and importing with a preview; [5.04, August 23, 2022](https://playvalorant.com/en-us/news/game-updates/valorant-patch-notes-5-04/) documents hex colors, independent axis lengths, spectated-profile copying and 15 profiles. The older icon placement is historical, rather than a current-client inspection.

Aimlabs evidence: the developer's [July 2021 pixel overhaul](https://store.steampowered.com/news/posts/?appids=714010&enddate=1628709535&feed=steam_community_announcements) replaces arbitrary size units with pixels. The official [December 7, 2021 tutorial's crosshair chapter, at 1:11](https://www.youtube.com/watch?v=cHLJaLKh-Cc&t=71s), shows importing a PNG and changing its size. [December 15, 2021 patch notes](https://store.steampowered.com/news/posts/?appids=714010&enddate=1649644433&feed=steam_community_announcements) document recoloring imported crosshairs. Aimlabs [2.0's September 2026 release](https://steamcommunity.com/games/714010/announcements/detail/710033888216351460) changed the UI; the exact current control inventory and menu labels were not verified. Generic theme/content sharing does not establish crosshair-code compatibility.

KovaaK's evidence: the [official creator](https://kovaaks.com/kovaaks/crosshair-creator) was inspected live by the trainer researcher on this date. Its controls describe the web creator, not a verified inventory of in-game sliders. The [official FAQ](https://kovaaks.com/kovaaks/faq) documents transparent PNGs from other editors, placing them in the game's crosshairs folder, and website share links. The [developer announcement, November 5, 2020](https://steamcommunity.com/games/824270/announcements/detail/2942500618556264352), also describes download/sharing. The parent web reader returned a JavaScript shell for the current creator/FAQ; the live inspection supplies that UI evidence.

These are different interchange mechanisms. The reviewed primary sources provide no public VALORANT code grammar or conversion API, and no verified trainer settings-code schema or promise that those trainers decode VALORANT codes. [Riot's developer documentation](https://developer.riotgames.com/docs/valorant) supplies no crosshair conversion endpoint. A hex color field is not a profile-code specification. Absence from this review is an evidence limit, rather than proof that a private implementation cannot exist.

## Recommended first outcome

Build a static center-crosshair editor with named local presets, one selected preset, native code import/export and persistence. Start with color/opacity, center dot, outline, inner/outer lines, length, thickness and center gap. Allow horizontal/vertical lengths to be linked or edited independently, plus a top-arm toggle. Keep the control list compact and show a live preview against dark, bright and arena-like backgrounds.

Opening the editor creates a draft. Paste Code or ordinary text paste, followed by Import, validates into that draft and shows the result. Apply selects and saves it; Cancel leaves the applied crosshair alone. Reset restores the default in the draft. Copy Code exports exactly the previewed draft. Creating or importing a preset gives it an editable local name; profile names need not travel in an appearance code. Crosshair preferences survive R, new runs and app restart. Invalid imports leave the current and draft profiles unchanged and explain the error.

Treat dimensions as explicitly defined pixels, and specify center anchoring, outline expansion and gap measured from the center to the nearest arm edge. The current HUD's 1280×720 scale makes one logical unit 1.5 physical pixels at 1080p. Before implementation, choose and demonstrate a consistent pixel/rasterization policy across resolutions; do not label scaled logical units as literal screen pixels or introduce shimmering half-pixel edges. Preserve the old benchmark crosshair rendering path exactly, independent of saved preferences. A human comparison should select the gameplay default size.

The first native format should have an application prefix, explicit schema version and bounded appearance payload; for example, an `SLCH:1:` envelope. This is our proposed format, not a vendor code. Specify the canonical field order, ranges, defaults and migrations before writing a codec. Do not commit to the researcher's fixed 20-byte option: independent axes and named preset storage need a considered schema. A checksum can detect accidental corruption, without authenticating the sender. Decode only bounded input, reject unknown versions and invalid values transactionally, and use the same validated appearance value for rendering, preview and persistence. Local storage failure should preserve session appearance and explain that saving failed. Keep storage operations outside the frame loop.

## Image imports and vendor adapters

Add transparent PNG import/export as the next bounded increment. It gives users a documented static-image path from KovaaK's downloads and Aimlabs-style image crosshairs. Preview the image's transparency, dimensions, center, tint and display size before Apply. An imported image is an image preset: its source sliders/layers cannot reliably be recovered. Exported PNGs are static snapshots; they do not transfer movement/firing-error animations or game-specific behavior.

An implementation contract must bound file bytes and decoded dimensions, manage texture ownership, and save a local copy so a preset survives deletion of its source file. Native appearance codes should not contain local paths or automatically fetch resources. Sharing image bytes requires an explicit file workflow; a short geometric code cannot recreate arbitrary pixels.

Keep direct VALORANT-code import as a separate source adapter, ahead of other undocumented vendor formats if requested. Establish the mapping using actual current exported fixtures and renderer comparisons. Show unsupported ADS/scope/dynamic settings and any approximation before Apply. Never silently accept unknown fields or describe visual similarity as native interoperability. Our validated static appearance remains the adapter's output; imported dynamic error settings must wait for a real accuracy model in this game.

## Fit with the existing prototype

The current [PrototypeGame center crosshair](../../prototypes/001-stacked-weapons/Assets/Prototype/Runtime/PrototypeGame.cs) is a fixed white plus. The useful cyan body brackets are a separate aimed-enemy identity cue in [CombatFeedback](../../prototypes/001-stacked-weapons/Assets/Prototype/Runtime/CombatFeedback.cs). White hit marks, gold kill marks, player-damage edges and world muzzle/tracer effects are also separate feedback layers. Customizing the permanent aiming mark must not remove those cues or encode HP/damage behavior in a share code.

No runtime preference service or crosshair editor currently exists. Use small appearance, renderer and codec/storage responsibilities rather than a general settings framework. Preview must use the actual reticle renderer without firing or querying enemies. Local crosshair preferences belong to each viewer in future cooperative play; they do not alter authoritative aim, damage, enemy state or progression. The reset path clears combat feedback while retaining player preferences.

[GDJ-17](https://linear.app/cnid/issue/GDJ-17/highlight-aimed-enemies-and-add-2-critical-head-hits) still owns valid-target coloring and pose-aligned ×2 critical hits. Later reactive colors must read the same target/region result used by firing, with a static-color option and identifiable feedback over any imported appearance. No spread/recoil display can be truthful until the weapon defines that state. Accessibility controls deserve human checks against crowded bright/dark scenes; available sliders alone do not establish accessibility acceptance.

## Verification for implementation

Use focused checks for codec round trips, malformed/oversized/unsupported-version imports and non-mutation on failure; Apply/Cancel/Reset, preset naming/selection and persistence recovery; preference survival across R/reload; centered rendering and clear units across resolutions; and unchanged aiming, damage and benchmark workload. Image support adds transparent-image, dimension/resource and missing-file checks. A standalone human session should import a shared preset, adjust it, restart, recover defaults and assess crowd/rapid-fire visibility. Serialize the pinned Unity tool operations when that feature is implemented. No new crosshair code, benchmark or human acceptance accompanies this research.
