## Longer-term test-harness recommendation

Owner selected this architecture on October 4 and requested [GDJ-21](https://linear.app/cnid/issue/GDJ-21/build-a-portable-game-test-interface-with-a-windows-background-runner): keep gameplay/simulation portable, the game-owned test interface independent of OS placement/transport, and a small native Windows runner outside game rules. Keep desktop placement, commands/state and frame delivery as separate adapters. Retain the Win32 desktop runner for concurrent local iteration without a second person or hardware requirement. Extend repeatable scenarios and event/state evidence through ordinary gameplay input/authority paths; desktop placement alone does not provide generic GUI automation. GDJ-21 owns the bounded interface/scenario/full-frame-capture/runner work; this PR supplies its starting prototype.

For smoother guided play, measure preview latency and capture cost, then consider an in-memory video pipeline instead of per-frame JPEG files. Capture the complete intended game presentation, including HUD, before treating the viewer as a substitute for native visual inspection. Preserve an instrumentation-disabled release path for controlled performance captures. A dedicated native Windows worker would be a later option when independent CPU/GPU capacity or real two-machine networking is needed; the same game bridge should remain usable there. A Windows GPU VM can be evaluated for broader desktop automation, but its graphics environment needs its own validation.

WSL is useful for Linux tooling, simulation/server workloads or a separately supported Linux player. It does not isolate this Windows executable inside Linux: [Microsoft's interop documentation](https://learn.microsoft.com/en-us/windows/wsl/filesystems#run-windows-tools-from-linux) states that Windows executables run as the active Windows user and appear as ordinary Windows processes. [WSLg](https://learn.microsoft.com/en-us/windows/wsl/tutorials/gui-apps) provides a Linux GUI/vGPU path, adding a different platform to validate. Keep native Windows as the primary player test environment for the current candidate.

The owner clarifies that the comparison should ignore existing work and assume a fresh start with a genuine Linux game/toolchain in WSL. The recommendation still favors native Windows for the current Windows client/performance envelope. WSL 2 provides a real [Linux kernel/managed VM environment](https://learn.microsoft.com/en-us/windows/wsl/compare-versions), useful for reproducible Linux automation and future Linux CI/server checks. Its rendered player uses a different [WSLg compositor/graphics path](https://github.com/microsoft/wslg#opengl-accelerated-rendering-in-wslg), so Windows rendering/input/performance validation would still need a Windows runner. [Unity 6000.3's supported Editor configurations](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html#editor) specify native workstations and platform-specific graphics/desktop requirements; WSL is not a listed Editor configuration. No comparative speed or reliability measurement has been made.

From the start, keep gameplay/simulation portable, the game-owned command/state/capture bridge independent of OS placement, and the small OS-specific launcher outside game rules. This preserves an option to build and validate a Linux runner later without redesigning gameplay. A Linux-first automated lab could favor WSL from inception; that is a different priority from the present native Windows player envelope. The current file/JPEG bridge is a prototype transport, not a prescribed final architecture. Windows plus a portable bridge is the selected follow-up; Linux/WSL implementation remains future work.
