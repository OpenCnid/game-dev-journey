## Separate desktop, control and capture

Owner explicitly requested a same-login **Win32 desktop object**, following [Strata DesktopProcess](https://github.com/OpenCnid/strata-bench/blob/f3b009e4b2a265633fdc86a6ff8b32984238ab5d/src/mcbench/desktop_process.py). The launcher uses CreateDesktopW and suspended CreateProcessW/STARTUPINFO.lpDesktop, binds the process tree to a kill-on-close Job Object before resume, monitors unchanged input context and bounds the session to 15 minutes. It never switches the input desktop or injects OS input. Actual pair launches/stops retain input desktop `Default`; only the final two owned Stack Lab processes remain running at this checkpoint. This shares the machine's CPU/GPU and same-user permissions.

Unity needs visible windows on the non-input desktop for rendering. SW_HIDE yielded black swap-chain and camera-texture images despite advancing simulation. SW_SHOWNORMAL on the separate desktop produces the actual arena/drone/rifle views while preserving the main input desktop. `-sharedPreview` supplies an in-process game bridge: live snapshots, sequenced/run/life-scoped ordinary input, autoplay/idle, terminal Retry and quit. Half-second host input moved 4.08 metres, then both movement and firing expired; the client stayed scripted. Inactive-player input rejects. Both-ready Retry increments run and resets both life identities; one-ready alone does not restart.

The camera renders at 1920×1080 into a texture, with asynchronous readback and 960×540 JPEG previews. Immediate-mode window HUD is separate; the viewer shows live shared state and a crosshair alongside the camera. Controls still pass through ordinary movement/shot/authority paths and cannot grant health/damage/deaths. Windows readers allow replacement while Unity atomically publishes state/images; sequences advance only after successful command publication.

P1 asked for a smoother view than the first two-frame/s preview. Continuous multipart streams target 30 Hz. The first transport poll delivered about 21 frames/s; polling more frequently preserves more source frames. The final [four-second simultaneous stream check](evidence/gdj-20-shared-v4/stream-verification.json) delivered **26.11 host / 25.82 client frames/s**, with every sampled JPEG changing during play. Both actual camera images and viewer were inspected. This is delivery evidence for the preview, not game frame-time or responsiveness acceptance.

Reproduce from the task checkout after a build:

The launcher prints a loopback-only viewer address and saves it in ignored results, with per-player frames/events/commands/state and terminal summaries. **Stop both games** closes the owned pair; a deadline or input-context loss also stops it. Both players have Retry controls. For native human role comparison, preserve `-ScriptedCompanion` and reverse `-HumanRole client` in the original visible launcher.

## Longer-term test-harness recommendation

Owner asks which environment is best in the long run. Recommendation, not an accepted migration or additional implementation scope: keep the native Windows player and application-owned bridge, with desktop placement, commands/state and frame delivery as separate adapters. Retain the Win32 desktop runner for concurrent local iteration without a second person or hardware requirement. Extend repeatable scenarios and event/state evidence through ordinary gameplay input/authority paths; desktop placement alone does not provide generic GUI automation.

For smoother guided play, measure preview latency and capture cost, then consider an in-memory video pipeline instead of per-frame JPEG files. Capture the complete intended game presentation, including HUD, before treating the viewer as a substitute for native visual inspection. Preserve an instrumentation-disabled release path for controlled performance captures. A dedicated native Windows worker would be a later option when independent CPU/GPU capacity or real two-machine networking is needed; the same game bridge should remain usable there. A Windows GPU VM can be evaluated for broader desktop automation, but its graphics environment needs its own validation.

WSL is useful for Linux tooling, simulation/server workloads or a separately supported Linux player. It does not isolate this Windows executable inside Linux: [Microsoft's interop documentation](https://learn.microsoft.com/en-us/windows/wsl/filesystems#run-windows-tools-from-linux) states that Windows executables run as the active Windows user and appear as ordinary Windows processes. [WSLg](https://learn.microsoft.com/en-us/windows/wsl/tutorials/gui-apps) provides a Linux GUI/vGPU path, adding a different platform to validate. Keep native Windows as the primary player test environment for the current candidate.

The owner clarifies that the comparison should ignore existing work and assume a fresh start with a genuine Linux game/toolchain in WSL. The recommendation still favors native Windows for the current Windows client/performance envelope. WSL 2 provides a real [Linux kernel/managed VM environment](https://learn.microsoft.com/en-us/windows/wsl/compare-versions), useful for reproducible Linux automation and future Linux CI/server checks. Its rendered player uses a different [WSLg compositor/graphics path](https://github.com/microsoft/wslg#opengl-accelerated-rendering-in-wslg), so Windows rendering/input/performance validation would still need a Windows runner. [Unity 6000.3's supported Editor configurations](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html#editor) specify native workstations and platform-specific graphics/desktop requirements; WSL is not a listed Editor configuration. No comparative speed or reliability measurement has been made.

From the start, keep gameplay/simulation portable, the game-owned command/state/capture bridge independent of OS placement, and the small OS-specific launcher outside game rules. This preserves an option to build and validate a Linux runner later without redesigning gameplay. A Linux-first automated lab could favor WSL from inception; that is a different priority from the present native Windows player envelope. The current file/JPEG bridge is a prototype transport, not a prescribed final architecture. This remains an advisory comparison.
