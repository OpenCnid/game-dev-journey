## Displayed pose and message policy

Publish small complete snapshots at 60 Hz. Initially display the exact latest snapshot's enemy transforms, avoiding undocumented interpolation rewind. Retain a bounded host pose history; each shot carries run, pose tick, source weapon/event, player life, ray, and local emission time. Host re-queries the retained displayed healthy/wounded body/head matrices, accepts only a recent pose, and checks current incarnation before damage. Never trust client region/damage/kill declarations. Nearest intersected surface/head tie remains the accepted query. A reused enemy slot cannot receive old-incarnation damage. Local camera is immediate; local movement prediction is reconciled against accepted input/position, and death/return resets it.

Process queued shots in stable source-ID/event order before contact/terminal checks. Positive-to-zero damage creates one immutable death snapshot before respawn. Actual damage is capped at current HP. Duplicate event sequences, invalid rays, obsolete run/life/weapon IDs, expired history and post-ending submissions reject; old-run retry messages reject too. Reliable transport does not replace application validation. Bound queue/history sizes and surface overflow/timeout failures. Retry increments run ID and clears pending queues, history, counters, cooldowns, readiness and feedback. Five-second return and one-second contact immunity use active authority time. All-dead defeat precedes duration completion and expiring return. Original solo and benchmark modes retain their own paths/preferences.

### Session architecture discussion — future reconnect and The Zone

The owner expects multiplayer to preserve the game's normal tuning and stresses that reconnecting after a disconnect is an important feature. GDJ-20's fixed feasibility fixture still aborts on connection loss; reconnect is not implemented or validated. This future requirement does not silently change the fixture's accepted disconnect check.

Recommended separation: one combat core/default configuration for solo and co-op; a session lifecycle for membership/configuration/readiness/start/return; and a replaceable connection/discovery adapter. A small lobby presents active settings and participants, clears readiness when configuration changes, and confirms the same configuration before starting. Explicit developer test overrides remain identifiable. Stage common configuration, a minimal two-player lobby, 1–4-player validation and measured dense replication as bounded work. The current one-peer connection, fixed two-player arrays/readers and complete 60-Hz enemy snapshots do not establish four-player or dense-network scalability. No new service/package or implementation scope is selected by this recommendation.

Reconnect is coordinated by the session lifecycle across the other responsibilities: retain stable player membership/identity for a bounded grace period; restore and authenticate a new connection to that membership; keep authoritative player/build/choice state associated with the player rather than the old socket; supply the current run/configuration/phase and world snapshot, invalidate old-connection inputs and acknowledge synchronization before resuming control. Repeated reconnect must not recreate grants, reroll offers or credit XP twice. Connectivity should be modeled separately from health/death. Grace duration, disconnected-character behavior, departure/expiry and terminal-state eligibility need explicit rules. Loss of the authoritative host process additionally needs host migration/state recovery or persistent server authority; reconnecting a client alone cannot supply that state. [Unity's session reconnect documentation](https://docs.unity.com/en-us/mps-sdk/join-session#reconnect-to-a-session) likewise distinguishes reconnecting a retained member from joining after removal; no SDK adoption is implied.

The pre-game lobby prepares a new run. The accepted [party thinking space / The Zone](../../decisions/0004-party-thinking-space.md) operates inside the existing run: physical combat and encounter clocks freeze, earned personal choices remain owned, and play resumes when eligible active participants are ready. It preserves run progress instead of starting a new encounter. UI/readiness primitives may be reused, but phase, allowed actions and participant eligibility remain explicit. Reconnect should restore whichever phase is current; network timeout/grace clocks should continue while physical time is frozen. A disconnected participant's effect on Zone readiness remains a rule to specify so a lost connection cannot create an indefinite wait. Exact grace, departure, readiness and host-loss policies remain open; no reconnect/lobby/Zone code was added.
